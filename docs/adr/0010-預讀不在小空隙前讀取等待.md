# 預讀不在播放器會直接播過的小空隙前讀取等待

預讀模式的讀取等待（[ADR 0005](0005-預讀透過緩衝擷取或影子播放器.md)）規則是：觀眾前方已翻譯、彼此相連的片段不足 0.15 秒時，就暫停主播放器。「相連」原本的意思是下一個片段從上一個片段結束處開始，最多容許 0.03 秒的誤差。

2026-11-18 第一次在 B 站實際使用 MediaSource 擷取（[ADR 0009](0009-預讀支援任何MediaSource播放器.md)），觀看一場 TED 演講時，影片停在 99.2 秒，一直顯示「讀取音訊中…」。91.72–99.3 秒和 99.33–113.35 秒兩個片段都已經翻好，只是 B 站播放器送出的音訊在 99.30 到 99.33 秒之間少了略多於 0.03 秒。影片的緩衝範圍（80.1–170.2 秒）是連續的，播放器本身會直接播過這個空隙；預讀卻判定相連的片段只到 99.3 秒，離觀眾只剩 0.1 秒，於是讀取等待。等待的是一段根本不存在的音訊，補讀也補不回來，所以永遠卡住。

因此，判斷觀眾前方有多少相連片段時，**片段之間不超過 0.1 秒的空隙視為相連**。

## 考慮過的選項

- **把收到的音訊在 0.1 秒內的空隙直接接起來**（把合併音訊區塊的 0.03 秒門檻放寬）：否決。接起來的音訊會讓空隙之後的樣本整體往前移，之後每個片段裡句子的時間都會偏掉一個空隙的長度。只在判斷是否讀取等待時跨過空隙，定時字幕的時間不受影響。
- **在擷取程式中用靜音補滿空隙：** 否決。要分辨真正的空隙與解碼器的時間誤差，而且 YouTube 與影子播放器的音訊也可能有同樣的空隙；在 session 處理一次就涵蓋所有來源。
- **把讀取等待的 0.15 秒門檻調低：** 否決。只要空隙出現在觀眾正前方，任何門檻都一樣會卡住。
- **讀取等待時跳過觀眾所在的空隙：** 否決。ADR 0005 刻意規定絕不跳過觀眾所在的空隙，因為那段音訊通常只是還沒到、補讀能帶回來；只有小到聽不出來的空隙才可以不等。

## 後果

- 0.1 秒與擷取程式重設解碼器的門檻相同：小於它的時間跳動，本來就視為同一段連續的音訊。
- 空隙裡沒有音訊，也就沒有可翻譯的內容，所以跨過它不會漏掉字幕。
- 代價是：如果擷取程式本身出錯，弄丟了不到 0.1 秒的音訊，預讀不會因此停下來，這種錯誤也比較不容易被發現。
